Coverify Simple System Design

Coverify should be a Cosheaf-first mathematical harness: an agent works on visible project state, calls tools when needed, and only durable checked progress is written back to Cosheaf.

Core Idea

Memory

Cosheaf

Owns durable mathematical state: pages, branches, issues, PRs, reviews, comments, labels, and merge decisions.

Harness

Coverify

Reads Cosheaf, builds bounded context, runs author/critic/tool calls, records audit artifacts, and writes checked summaries back.

Engines

Tools

LLMs, provers, checkers, compute scripts, and external workflows are tools. They do not own project memory.

Invariant. If a mathematical action matters after the process exits, it must become a Cosheaf artifact. Local files are audit, cache, or scratch.

One Primitive: Attempt

An attempt is the simple unit that absorbs the useful part of an Author/Critic workflow without copying a large workflow framework.

Part Lives In Purpose
Problem or task Cosheaf issue Defines what is being attempted and any constraints.
Current work Cosheaf branch Holds the candidate solution, notes, computations, and failed-route pages.
Author output Branch edits plus issue summary Moves the mathematical state forward.
Critic output Issue comment or PR review Checks correctness, labels gaps, and decides whether the attempt is ready.
Raw calls .coverify/runs Stores prompts, answers, stdout, stderr, metadata, hashes, and workflow traces.

Attempt Loop

1. Read

Load issue, branch files, project orientation, and last critic report.

2. Author

Ask an author model or workflow to propose branch edits and a short summary.

3. Apply

Validate paths and update the Cosheaf branch. Keep raw output in the audit dir.

4. Critic

Fresh critic reviews the current branch and writes objections or readiness.

5. Decide

Continue, record failure, open PR, request review, or merge accepted progress.

coverify attempt run --workspace owner/repo --issue 12 --rounds 3

Author And Critic Mapping

Author

What It Does

  • Reads the issue and current branch snapshot.
  • Produces a patch or complete replacement for configured attempt files.
  • Writes durable notes for facts, partial routes, and failed routes.
  • May call tools, but useful outputs must be summarized back to Cosheaf.
Critic

What It Does

  • Reviews the current branch, not hidden conversation state.
  • Checks target fidelity, proof gaps, source support, and status labels.
  • Writes a review comment or PR review with exact objections.
  • May say ready only when the current branch is actually ready.
Simplification. Default critics are fresh. If memory matters, put it in Cosheaf notes or prior review comments, not in a hidden critic conversation.

Tools Stay Tools

Coverify should call tools through stable surfaces and keep their outputs auditable. It should not make every tool into a new core mode.

Need Surface Notes
One LLM or prover call ask-oracle or backend runner Prompt in, answer out, audited.
Project checker or score script tool run Declared in coverify-tools.json.
Large external workflow workflow run Problem file and output directory passed by placeholders.
First Proof style workflow firstproof run Preset wrapper over workflow run, not the architecture.
Fixed parallel pipeline Optional DAG later Only when the graph is stable and useful across runs.

What Not To Copy From Improofbench

Avoid In Core
  • General DAG runtime as the default path.
  • Hidden long-term local project memory.
  • Stateful critic conversations as correctness state.
  • Visual workflow metadata before a real need exists.
  • Provider framework duplication inside Coverify.
  • First Proof LaTeX rules as global assumptions.
Keep The Essence
  • Iterative authoring under strict critique.
  • Visible working files that persist across rounds.
  • Explicit readiness gates.
  • Optional computation and external workflow calls.
  • Strong audit trail for every model or tool call.
  • Clear distinction between partial progress and solved.

DAG Position

DAG workflows are useful as advanced reusable tools, not as the default mental model. They make sense when a graph is stable, parallelism matters, and inputs/outputs are mechanical.

generate candidates -> verify candidates -> improve failures -> merge best -> final review

The normal path remains an adaptive attempt loop over Cosheaf state.

Minimal Command Shape

# Start or continue a Cosheaf-backed attempt
coverify attempt run --workspace owner/repo --issue 12 --rounds 3

# Inspect what the next author or critic would see
coverify attempt prepare --workspace owner/repo --issue 12 --role author --json

# Call a project-specific checker
coverify tool run check-candidate --message-file candidate.json --json

# Call a larger reusable workflow
coverify workflow run --cwd /path/to/workflow \
  --command 'python run.py --problem {problem_path} --output {output_dir} --run-id {run_id}' \
  --message-file problem.tex --json

The exact command names can change. The important design is attempt-first, Cosheaf-first, tool-friendly.

Build Order

  1. Define attempt state: issue, branch, attempt files, status, last review.
  2. Add prompt preview for author and critic roles before model calls.
  3. Implement one round: author patch, mechanical validation, branch write, critic review.
  4. Persist summaries to Cosheaf and raw calls to audit directories.
  5. Add repeat, stop conditions, and PR/merge behavior.
  6. Only then consider optional DAG presets for stable portfolio workflows.
Design rule. Do not add a new workflow abstraction when a Cosheaf issue, branch, PR, review, and one tool call are enough.
